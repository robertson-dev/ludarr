# ludarr — notes for working in this repo

- Bun 1.3 + TypeScript; Hono HTTP; bun:sqlite. `bun test` (166+ tests, in-memory DB via tests/setup.ts), `bun run typecheck`, `bun run dev`.
- The engine came from the Ahoy backend in October 2026. Since 2026-11-05 **Ahoy** (the ahoy folder beside this one: its own server, web UI and the desktop launcher, container `ahoy` on :8790) is ludarr's only client: it holds the API key and uses /game, /package, /crackwatch/lookup, /art/game, /system/events. Nothing player-facing (accounts, friends, discovery rows, the launcher) belongs in ludarr; `launcher/`, `web/src/ahoy`, `src/metacritic.ts`, `src/api/launcher.ts` and the launcher-only tail of `src/discover.ts` are dead copies waiting to be deleted. Do not break `src/bosun/*` compatibility: the same connector binary runs on the user's seedbox.
- Everything configurable is either a global setting (`src/config.ts`, env → saved → default, Ahoy's AHOY_* names accepted as aliases) or a plugin instance (`src/plugins/registry.ts`, table `plugin_instances`). Built-ins are plugins (`src/plugins/builtin/*`).
- API: `/api/v1/*`, `X-Api-Key` required (key in kv `host.apiKey`, injected into index.html as `window.ludarr`). Each `src/api/*.ts` header lists its routes.
- Tests swap `deps`/`rdeps`/`sdeps`/`pdeps`/`cdeps` objects instead of mocking modules.
- Deploy to the user's Unraid with `UNRAID_PASS=… python deploy/unraid.py` (builds on the box, installs `unraid/my-ludarr.xml`, container `ludarr` on :7979). Check nothing is downloading/importing first.
- Shell gotcha on this machine: Bash heredocs break on backticks — write files with the Write tool.
- A file on disk is read whole (hashed, copied) only through `fileChunks` (`src/fsutil.ts`): its reads happen off the server's thread. Never loop over `Bun.file(path).stream()`: on Linux that keeps the thread until the file ends, and the whole server (pages, API, every player's download) stood still for as long as an import hashed its files (2 min 44 for 26 GB, seen live 2026-11-11; Windows does not show it, so a local run looks fine). `tests/file-reads.test.ts` refuses a new `.stream()` call in `src/`.
- A package is also sent as blocks (`src/blocks.ts`, `src/api/blocks.ts`; the launcher's side is `src/pull/blocks.ts` in ahoy-launcher, Ahoy passes the two routes through): every file cut at each MiB, each block named by its sha256, an index per package in `<config>/blocks/<id>.blk` (never in the package's folder, which stays plain files: the ways are built on them). The index is tied to the manifest's file list by a digest (`filesDigest`), written by an import from the same read that makes the manifest (`buildManifest` `o.blocks`), and by the task `blocks` for packages without one (one package a run, never while a job runs, never over a file whose sha256 is not the manifest's). Blocks are a faster way to the same files, never the only way: the per-file route stays, and a launcher falls back to it whenever blocks are missing or cannot be trusted. A change to the frame or index format needs both sides and a new magic.
- A game's files uploaded from the admin's PC (game page → Upload): `src/uploads.ts` + `src/api/uploads.ts` (a staging folder `<root>/.ahoy-uploads/<id>/<name>/`, pieces appended at an offset, `.ahoy-part` until a file is whole, then an ordinary import job with spec `{ upload }` or a content job for a way; the staging folder goes when the job took it in). The browser side is `web/src/uploads.ts` (the sender, free of React: `tests/web-uploads.test.ts` drives it against the server module) and `web/src/ui/upload.tsx`. A copy imported from an upload has manifest `source.protocol: "upload"` and install class `uploaded`: no upgrade search replaces it.
- TENOKE's SETUP.bin is read directly by `src/process/tenoke.ts` (format recovered from the installer with a decompiler: XOR-scrambled records, Snappy/zlib/stored bodies, see the file header); `tests/tenoke-pack.ts` builds packages for tests. Inno installers run with `/LOG`, and the log is the finish/activity signal (`runInstallerUnderWine`); payload parts are only handed to `7z l` when their first bytes carry an archive signature (`partSignature`).
- Import recipes live in `src/process/recipes.ts` + `scene.ts`. Installers without a silent mode (an unreadable TENOKE build) are driven by `helpers/dlgdrive.c`, a Win32 helper compiled with mingw in the Dockerfile's `wintools` stage and run under wine on the installer's own virtual display (`dialogInstallCommand`). The AI importer gets every earlier lesson in its prompt (`priorLessonsFromJobs`); after turning a lesson into a recipe, PATCH /api/v1/import/:id/lesson {adopted}. Test a new installer layout on the box: build with `docker run --rm -v /tmp/dlg:/src dlgdrive-builder x86_64-w64-mingw32-gcc -O2 -s -municode -o /src/dlgdrive.exe /src/dlgdrive.c -lgdi32 -luser32`, `docker cp` it into the container, run it with `--dump` / `--shot` / `--probe` in a scratch WINEPREFIX.
